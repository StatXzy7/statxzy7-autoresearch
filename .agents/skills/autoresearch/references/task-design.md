# 任务设计

明确输入、输出、目标指标、优化方向、质量约束和可修改范围。将研究问题落实到实际被评价器调用的方法接口；检查候选确实能替换算法步骤，而非只能修改未被调用的文件。

## 数据与评价

划分训练、开发与最终评价数据。开发评价返回原始指标、错误诊断和任务允许的反馈；最终评价只在候选冻结后进行。固定数据版本、样本索引、预处理、评价器和预算规则，并用协议 ID 绑定。若缺独立最终数据，明确只具备开发证据，不把它外推为泛化结论。

评价器从实际预测或数值产物计算指标，检查形状、类型、有限数值和质量约束。提前说明无效输出、超时、资源耗尽与基础设施故障的处理方式。不要让候选直接填写最终奖励，或在质量检查失败后仍按分数排序。

## 公开与私有材料

公开工作区仅包含允许的起点、数据、接口、评价入口和说明。构建挑战任务时，参考方案、目标推导中的解法、最终标签和完整优化证据保存在可信侧。目录命名不能提供隔离：检查文件权限、挂载、工具访问、环境变量、日志、同用户进程与提权路径。

评分代码、固定协议和可信结果目录应受保护。验证候选无法改写评价器或读取最终标签；环境无法提供这些边界时，报告限制，不能声称受保护评价已就绪。

## 任务说明

按 [任务说明模板](../assets/instruction.md) 给出背景、输入输出、方法接口、评价、约束、预算和提交方法。使用仓库相对路径；确保示例命令在干净工作区可运行。提交范围应足以重建方法、配置及必要模型。

对照、候选池、模型通道、搜索预算、seed 协议和最终选择规则在比较前冻结。更改数据、训练量或评价口径时创建新协议并补跑对照，保留先前协议和失败记录。

## 可改进性

任务应有健康可执行的 Baseline 和能改变结果的合理方法空间。构建需要证明可解性的任务时，作者侧先运行独立参考方案，确保改善来自合法方法，并保留同协议配对证据。不要用候选运行结束后的最佳分数反向定义任务难度。
